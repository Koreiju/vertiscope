# Sensor contact audit: does the browser cell touch the page?

Date: 2026-10-04. Branch `feat/plugin-goal-projector`, HEAD `2fcc022`. Read-only research: code and git history only, the app was not run and no probe was executed.

The claim under test (user, `docs/PLUGIN_GOAL.md` ~l.2113-2118, the uncommitted addendum): the Electron scan should "completely avoid any detectable injection except for required mutationobservers, but with zero contact with 'the page itself' such that we don't throw off trackers or even break pages". The binding form is `CLAUDE.md` rule 7: "Nothing is written into the page; nothing is transmitted."

Marking convention: **[code]** read directly in the file cited. **[history]** quoted from a commit. **[unverified]** an inference or outside knowledge that this audit did not test.

## 0. Verdict

1. **The literal rule, "nothing is written into the page", holds for the DOM.** `sensor.js` never calls `setAttribute`, `removeAttribute`, `classList`, `.style` or `appendChild` on the page (grep over the whole file: no hits). The Obsidian host draws every overlay in its own DOM. [code]
2. **The stronger goal, "zero contact" / "no detectable injection", is not met.** The sensor is installed by `webview.executeJavaScript` into the page's **main world**, parked on `window` under a **fixed, publicly-named** property (`__vertiscopeSensor`). It then runs entirely on the page's own, patchable globals, registers page-side listeners, forces layout reads inside the page's task, and uses the page's `console` as a push channel. Section 1 lists each contact.
3. **The repo already knows this.** Three of its own commits say a non-enumerable property is still listed by `Object.getOwnPropertyNames(window)` and that the real fix is hosting outside the main world (`2a0e646`, `bb251c0`, `616ab95`). The Electron host then went back to a fixed name (`33f0c85`) and a comment at `browser.ts:56-61` justifies that choice. The completed isolated-realm work was never done on either host.
4. **Electron's isolated world was never considered.** `git log -S` for `executeJavaScriptInIsolatedWorld`, `contextIsolation` and `worldId` over all history returns nothing. The only isolated-world ideas in the repo are Firefox's BiDi sandbox realm (scaffold only, `616ab95`) and a passing phrase in a research JSON (`d567970`). See section 3.
5. **No test asserts the page-visible footprint of the Electron host.** Grep for `getOwnPropertyNames` or any property-listing probe over `tests/`, `obsidian-plugin/checks`, `obsidian-plugin/tests`, `vertiscope/analytics` finds nothing relevant. The "nothing is written" claim has no non-vacuity arm, which is exactly the defect class `CLAUDE.md` warns about.

### 1.5 Things that are clean

- No DOM writes, no `data-*` stamping, no `<style>` / `<script>` injection by the sensor. `data-vertiscope-hash` stamping existed in the baseline serializer (`e4d735c:vertiscope/core/js/deep_serialize.js:216`) and does not exist in `sensor.js`.
- `executeJavaScript` is Electron's own frame execution, not a CDP `Runtime.evaluate`; the `Runtime.enable` / `ExecutionContextId` leak (research, `d567970`) needs a CDP client with `Runtime` enabled, and none is attached by shipping code (row 5, 22). [unverified against Electron 39 internals: this is knowledge from outside the repo]
- `allowpopups` is off (`B:347-349`).
- State lives in `WeakMap`/closure, not on page objects (`S:12-14`).
- Closed shadow roots are left closed; the sensor does not patch `attachShadow` (`S:1066-1070`). That decision is the strongest evidence in the code that the zero-contact principle was taken seriously.
- Hidden / password inputs are skipped (`2a0e646`, `3f662a1`), so tokens do not enter the store.

### 2.3 Approaches that were **not** used (checked)

- **Playwright**: appears only in the research corpus and `PLUGIN_GOAL.md` notes (2029a73, 2026-09-12: Playwright can drive Electron over CDP). Never used as the capture path.
- **CDP as the sensor's read channel for the Electron cell**: stated as the plan in `B:21-22` and `f16720c`, never implemented; `webContents.debugger` is used only in probes (G-38 `Overlay.*`, withdrawn in `701aea3`).

- **`Page.addScriptToEvaluateOnNewDocument`** (pre-page-script injection): appears only in the research JSON. Not used. The Electron analogue, a `<webview preload>`, was named as the injection point (`5eb1533`, `PLUGIN_GOAL.md` ~l.2310) and not built.

### 2.4 Which later findings negated or confirmed which earlier designs

- **Confirmed** (by measurement): single document-level observer plus fold as the sensor (DESIGN_SPACE variants A/B; `perchunk` is off by default, `S:106`); push over pull for latency (`ff322dd`); layout as peripheral not fold (`invariants.c2`).
- **Negated**: "nothing about it is guessable from the page" (`2a0e646`); fixed `window._wfhEngine`/`__s` (fixed by `2a0e646`/`bb251c0`, re-introduced by `33f0c85`); "constraint 7 forbids [a page listener]" (G-38, 09-19) vs `ff322dd` (09-27); "Nothing is injected into the page and nothing will be" (`f16720c`) vs `33f0c85` the same day-range.
- **Withdrawn / open**: isolated hosting (`616ab95`) has no later commit.

## 3. Electron `executeJavaScriptInIsolatedWorld`

**Was it ever considered?** No. Evidence:

- `git log -S` over all history for `executeJavaScriptInIsolatedWorld`, `contextIsolation`, `worldId` returns zero commits; the working tree (excluding `node_modules`, `.git` and the built bundle) has no occurrence outside this file.
- The words "isolated world" appear only inside the research JSON `d567970:.../MutationObserver_semantics_and_blind_spots.json` (as "an extension's isolated world sharing the same loop", a description of Chrome extensions), not as a design option.
- The repo's only "hosting outside the page's main world" work is the **Firefox BiDi sandbox realm** (`616ab95`, `vertiscope/config.py:30`, `vertiscope/browser.py:118-124`), scaffolding only.
- The S-13 verdict (`5eb1533`) lists `preload` and `webContents.debugger` as the injection points and says nothing about a world.

**Does the current main-world install contradict the zero-contact rule?** Yes, on the strong reading ("no detectable injection", user's own words) and no on the weak one ("nothing is written into the page", `CLAUDE.md` 7).

- Contradicting: rows 1-3 (a page-visible handle that a page can call), row 8 (page-side listener), row 11 (console as a transport), row 9-10 (layout reads and timers inside the page's tasks), and every builtin the sensor calls is a page-patchable global (`MutationObserver`, `addEventListener`, `JSON.stringify`, `Object.defineProperty`, `queueMicrotask`, `Function.prototype.toString`). A prototype-patching library loaded before boot (Prototype.js `Array.prototype.toJSON`, zone.js, session-replay SDKs) changes what the sensor does. [unverified: not measured on any page; recorded as a structural risk]
- The project's own `616ab95` message says hosting "outside the page's main world" is "what closes the handle-visibility leak". That is the same diagnosis an isolated world would address.

**What an isolated world would and would not change** [unverified: Electron behaviour, not tested here]:

- An isolated world shares the DOM (so a `MutationObserver` on `document` and shadow roots works) but has its own JS globals: `window.__vertiscopeSensor` would not appear in the page's `getOwnPropertyNames`, and a page's patches to `JSON`, `Array.prototype`, `Function.prototype.toString` would not apply to the sensor. That removes rows 1-3 and the patched-builtin risk.
- It would **not** remove: DOM-level observers' costs, forced layout (rows 9, 14, 18), scroll side effects (row 15), listeners on shared DOM nodes (a page could in principle observe event-listener side effects through timing), or the console channel (the isolated world has its own `console`, but its messages still reach the host's `console-message` event; whether a page-side `console` wrapper sees an isolated world's calls was not checked).
- `<webview>` exposes `executeJavaScript` (main world) but not an isolated-world variant; the usual routes are a `<webview preload>` with `contextIsolation`, `webFrameMain` / `webContents` via `@electron/remote` (reachable per `5eb1533` N.1), or CDP `Page.createIsolatedWorld`. CDP routes re-introduce a debugger client (row 22). Which of these works for this Obsidian-hosted `<webview>` is the open question; `preload` for a `<webview>` must be a file path, which touches the "single sensor file served by the sidecar" decision in `33f0c85`.

## 4. Smallest set of facts the user can act on

1. The handle name is a fixed signature (`B:62`, `P:44`) while `2a0e646` and `bb251c0` set the opposite policy for the Selenium host. A random per-load name needs only `HANDLE` generated once per plugin load and passed to `pipelinebox`; that lowers the cost of detection from one string compare to a diff against a clean `window`, as `2a0e646` itself says ("does not make it unfindable").
2. Only an isolated world (or running the fold outside the page and shipping serialized DOM) removes the handle and the patched-builtin exposure; nothing in the history has measured the cost, and the one measurement `616ab95` promised was never run.
3. The listener (`S:2978`) and the layout reads (`S:2518-2519`) were each added without a recorded decision against `G-38` / the zero-contact principle. `docs/PLUGIN_PRD.md` G-38 and G-39 still say "nothing listens inside the page".
4. The console channel (`S:48-52`, `B:382`) carries page content through the page's own `console`; its safety rests on a `toString` check that a hostile or merely wrapping page can defeat before boot.
5. There is no test of the footprint. A non-vacuity test would plant a hostile page that wraps `console.debug`, lists `Object.getOwnPropertyNames(window)`, patches `MutationObserver` and `addEventListener`, and assert what it sees, then re-run after any change to the install path. `vertiscope.analytics` was checked first per `CLAUDE.md`: `--anonymity` (`d3283f0`) measures Firefox hardening preferences against the fold, not page-visible footprint, so it does not answer this.

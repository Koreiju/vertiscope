## What the libraries in hand force

Documentation read through Context7 (`/vasturiano/3d-force-graph`,
`/mrdoob/three.js`), 2026-09-28.

| fact | what it forces |
|---|---|
| 3d-force-graph draws `nodeThreeObject(node)` per node and picks by raycasting those objects | one object per node must remain, or picking dies (demand 3) |
| three.js skips drawing an object whose `material.visible` is false; `Raycaster` still intersects it (it tests layers, not visibility) | the per-node object can be an invisible proxy: pickable, zero draw calls |
| `linkVisibility(false)` removes the per-link objects; `scene()` and `renderer()` are exposed for custom objects | edges can be drawn by our own `LineSegments` added to the graph's scene |
| setting `graphData` pauses the engine and re-digests later (`onChange: engineRunning = false`) | the batch must read the CURRENT arrays each frame, never cache them across a digest (the D-38 lesson) |
| `gl_PointSize` is capped by `ALIASED_POINT_SIZE_RANGE` | points cannot carry close-up nodes; quads can |
| transparency is sorted per object, not per instance | translucent streaming nodes need their own mesh |
| `InstancedBufferGeometry` + `InstancedBufferAttribute` + a `ShaderMaterial` draw N quads in one call | the core of the design |

## Candidates

| candidate | what it forces | demands failed | decision |
|---|---|---|---|
| A. per-node sprites, textures shared via an atlas | still one draw call per node | 1 | no |
| B. `THREE.Points` + atlas, size attenuation | point-size cap; square only | none outright; close-ups clip | no |
| C. **instanced camera-facing quads, atlas UV per instance, sphere impostor when no picture** | a custom shader; two meshes (opaque, translucent); a line batch | none | **chosen** |
| D. `DataArrayTexture` (WebGL2 texture array) for unbounded atlas pages | WebGL2 only; more shader surface | none | deferred: one 4096² page holds 4,096 pictures, 1,476 in use |

## Full-stack path

The sidecar places a chunk (`/place`, `/layout`) → the pane builds the node
(`nodeFrom`: position from the fit, `image.src`) → the picture is fetched once
(`GraphView.textures`, a data URL) → drawn into an atlas cell (64 px, aspect
kept) → the atlas texture is uploaded (throttled) → the instance's `uvRect`
points at the cell → the fragment shader samples it, or shades a lit sphere
impostor when there is none → pixels. Back up: the pointer ray hits the node's
invisible proxy → the existing hover / click / right-click handlers. Nothing in
this path writes the layout.

## Revised by the other face

- The shape's "node cloud" became **two** instanced meshes after the
  per-object transparency sort (see the uml face).
- The shape's "points" became **quads** after the point-size cap.
- The api face wanted a texture array (D) for unbounded pictures; the shape's
  bound -- memory by atlas pages, and today's 1,476 pictures -- showed one page
  suffices, so D is deferred until a store outgrows 4,096.

## How this could be wrong

The sphere impostor is shaded in the quad's plane; it reads as a sphere from any
angle but its depth is the quad's, so two spheres interpenetrating by less than
a radius may sort by quad rather than by surface.

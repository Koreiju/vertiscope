## The module

`obsidian-plugin/src/scenebatch.ts` -- no dependency on the pane beyond three.js:

- `new SceneBatch(scene, capacity)` -- allocates the instanced quad geometry
  (opaque, translucent), the line batch, and the 4096² atlas canvas.
- `sync(nodes, links, radiusOf, colourOf, pictureOf, alphaOf)` -- called once per
  animation frame; writes instance attributes (offset, size, colour, uvRect)
  and line endpoints; grows the buffers by doubling when a graph outgrows them.
- `picture(src, img)` -- places a decoded image in a free atlas cell; the atlas
  upload is coalesced (≤ one per 100 ms).
- `stats()` -- draw calls, instances per mesh, atlas cells used, sync ms: the
  harness's render stage.

## In `graph.ts`

- `nodeThreeObject` returns a **pick proxy** per node: a shared unit sphere with
  an invisible material, scaled to `drawnRadius` -- raycast, never drawn.
- `linkVisibility(false)`; the batch's `LineSegments` draws every edge.
- A `requestAnimationFrame` loop calls `sync` while the pane is open.
- `plantPerNode` (the planted arm) restores the old per-node objects and links.

## Patterns inherited from the API

- instance attributes are `InstancedBufferAttribute`s with `DynamicDrawUsage`,
  updated in place and flagged `needsUpdate` -- the three.js particle examples'
  own pattern;
- the translucent mesh has `depthWrite: false` and renders after the opaque one
  (`renderOrder`), as three.js orders transparent objects.

## What building it changed (2026-09-28)

The module landed with a different surface than the plan above, and each
difference was forced by something found while building it:

- **No coalesced atlas upload.** The plan re-uploaded the atlas at most every
  100 ms. A 4096² RGBA page is 64 MB; re-sending it for every new favicon
  stalls frames. three.js r185 has `copyTextureToTexture(src, dst, region,
  position)`, so each picture is drawn onto a 64 px canvas and copied into
  its own cell. The atlas itself is allocated storage-only
  (`source.dataReady = false` → `texStorage2D`, no upload), so the 64 MB never
  exists in the JS heap either.
- **`sync(nodes, links, look)`** takes one function returning the node's
  whole look (`NodeLook`: half-extent, translucency, alpha, colour, picture)
  instead of four accessors. The pane's `lookOf` is the one place those
  choices are made, and `drawnAs(n)` answers the checks from the same
  function, so a check never reimplements the renderer (G-21's lesson).
- **Stored spheres are opaque.** 3d-force-graph drew them at its default
  `nodeOpacity` 0.75; instances in one mesh cannot be depth-sorted against
  each other, so blending them would depend on buffer order. Opaque stored
  nodes also make streaming (translucent, G-93) the only see-through thing
  on screen.
- **The shader converts colour space** (`#include <colorspace_fragment>`).
  Without it, colours arrive linear and draw darker than the per-node ones.
- **Measurement is part of the module's contract.** `renderStats()` reports
  draw calls per frame (with `info.autoReset` off, so a multi-pass frame
  is counted whole), `renderer.render` CPU ms, frame gaps, textures and
  geometries. Frame GAPS turned out to be useless as a bar: a background
  Obsidian window is throttled to ~1 Hz whatever is drawn, so the gaps read
  1,000 ms in both arms. The render call's CPU time does not have that
  problem.
- **A second planted arm:** `plantNoPick`, proxies the raycaster cannot hit,
  so picking has a failing arm as well as a passing one.
